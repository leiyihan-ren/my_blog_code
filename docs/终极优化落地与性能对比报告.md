## 二、五项优化逐项说明

### 1. 失效占位图：从「失败后好看点」到「根本不发请求」

**问题**：后台示例数据里带 `https://example.com/cover.jpg`，每个页面都白扔一个
**620~1900ms 的 FAILED 请求**，控制台刷红。

**第一版方案**：新增 `icons/placeholder-cover.svg`，用捕获阶段的 `error` 监听兜底。
但这只让失败后「好看点」，**请求本身照发**。

**最终方案**：识别 IANA 保留示例域名（RFC 2606 / 6761），**渲染前就不请求**：

```js
// utils/blog-utils.js
const DEAD_SAMPLE_HOSTS = ["example.com", "example.org", "example.net", "example.edu"];
function isDeadSampleUrl(s) { /* ... */ }
```

`components/music-player.js` 在渲染封面和 MediaSession artwork 前先过滤，
命中则直接用 🎵 图标降级。

> **踩坑**：全局兜底一开始会抢占 `BlogApi.github.loadImage` 的多镜像降级链路
> （换上占位图后图片立刻加载成功，`onerror` 不再触发，三级镜像全废）。
> 修复：跳过带 `data-mirrors` 的图片；音乐封面带 `data-noFallback`，
> 因为「🎵 图标」比「占位图」更合适。

### 2. 阻塞脚本：代码侧不可控，已给出处置建议

线上 HTML 里确实存在：

```html
<script defer src='https://static.cloudflareinsights.com/beacon.min.js'
        data-cf-beacon='{"token": "bbb8a42692674c8b88a9c6d840ae8ba7"}'>
```

**结论**：这是 **Cloudflare Web Analytics 平台注入**的，不在本仓库代码里，
**已经是 `defer`**（不阻塞解析），代码侧无法改成 `async` 或用 `requestIdleCallback` 延迟。

**但它确实是 LCP 波动的最大来源**，实测耗时：

| 第三方请求 | 实测耗时区间 |
|---|---|
| `GET beacon.min.js` | 822ms ~ **2658ms** |
| `POST /cdn-cgi/rum` | 836ms ~ **2136ms** |

**建议**：若接受牺牲访问统计，可在 Cloudflare 控制台关闭 Web Analytics，
预计可消除 1~2.7s 的尾部延迟与抖动。这是本次唯一需要**人工在后台操作**的项。

### 3. 🚨 相册缩略图（最高优先级）

**实测元凶**：单张原图 **549KB / 2456×1600**，经 Worker 代理拉取 **2359ms**。

**为什么不用 Cloudflare Image Resizing**（逐条实测证伪）：

| 方案 | 实测结果 |
|---|---|
| `/cdn-cgi/image/width=400/...`（静态源） | **404**（免费计划未启用） |
| `/cdn-cgi/image/.../https://cdn.jsdelivr.net/...`（远程源） | **404** |
| 对 Worker 代理路径（需鉴权） | **401**，resizer 取不到源 |

**落地方案**：仓库内预生成缩略图。

| 指标 | 原图 | 缩略图 | 收益 |
|---|---|---|---|
| 体积 | **549KB** | **9.3KB** | **↓ 98.3%** |
| 尺寸 | 2456×1600 | 480×313 | — |
| Worker 代理拉取 | 2359ms | **715ms** | **↓ 70%** |

配套改造：
- **镜像链** `thumbs ++ mirrors`：缩略图全部失败时自动回退原图，历史照片无缩略图也不影响功能
- **灯箱渐进式**：缩略图秒开 → 后台拉原图 → ready 后无缝升级（不再干等 2.3s）
- **预取与相邻预热**只取缩略图（9KB），不再为「可能翻到」提前下载 549KB 原图
- **首屏立即加载**：前 3 张有缩略图的直接加载，不等 observer
  > 注意 `<img>` 没有 `src` 属性，HTML 的 `loading="eager"` **对它不生效**，
  > 加载时机完全由 JS 侧决定，必须显式调用 `loadImage`。
- **`scripts/gen-album-thumbs.py`**：新增照片可一键补生成（幂等，已含 480px / q72 参数）

### 4. 残余重复请求：收益 + 两个严重回归

**网盘口令验证**：验证接口与列表接口本是同一个（`/api/drive/list`），
旧逻辑验证成功后又立刻 `loadList()` —— 同一份数据请求两遍（实测 673ms + 154ms）。
修复：抽出 `renderListData(data)` 复用验证响应，二次请求消失。

**图片加载状态锁**（本次新加）引发的两个回归，均由测试套件抓出：

| 回归 | 现象 | 根因 | 修复 |
|---|---|---|---|
| 多镜像降级**整条废掉** | step2 B6 三组场景全挂 | 状态锁加在了**递归路径**上，第一个镜像失败后 `onerror` 调回 `loadImage` 被锁 `return` | 锁只加在**外部入口**，降级走内部 `tryNext()` 递归 |
| 灯箱 loading **卡死**遮住翻页按钮 | step3 UI 压测超时 | 锁在**成功路径上没有释放**，第二次打开灯箱被当成重复调用挡掉，`onSuccess` 不执行 | 加载结束（成功/失败）均释放锁 |

> 这两个 bug 说明「入口防重」和「链路降级」是两种不同语义，
> 用同一把锁覆盖必然踩坑。修复后 step2 相册 **64/0**、step3 UI 压测 **27/0**。

### 5. 统一网络层

`blog / post / links / timeline / games / guestbook` 共 **20+ 处裸 `fetch`**
全部接入 `BlogApi`，统一享受：

- **3s 熔断**（读）/ **12s**（写，避免误中断真实提交）
- **并发去重**：同一 URL 的并发读只发一次
- **LocalStorage 兜底 + 离线横幅**：失败自动回退缓存，页面顶部提示「网络不稳定，当前展示的是本地缓存数据」，**永不白屏**
- **统一错误对象**：4xx 不重试（客户端错误重试无意义），5xx 走指数退避

`admin.html` 的 30+ 处保持原样：后台管理需要精确的逐条错误处理，
且不影响首屏，改动收益低、风险高。

## 三、🔥 额外揪出的两个 P0：Cache API 缓存永不失效

部署后验证线上代码时发现：CI 部署成功，但线上 JS 里**查不到新加的函数**。
排查后确认是我上一轮为提速引入的缓存踩了同一个坑 ——

> **Workers 的 Cache API 会忽略 `Cache-Control` 响应头。**
> 条目不设 TTL 就不会自动过期，只能等 LRU 淘汰。

| 位置 | 问题 | 后果 | 修复 |
|---|---|---|---|
| 静态资源 | 直接用 `request` 作 cache key | 某次发版写入后，**之后无论部署多少次，边缘都一直吐旧文件** | key 拼入 `CF_PAGES_COMMIT_SHA`，发版后 sha 变化、旧 key 自然落冷；拿不到 sha 时（本地 wrangler）宁可不缓存 |
| API 缓存 | 只设 `Cache-Control: max-age` 就 `put` | 文章/歌单/相册一旦进缓存就成了「**化石**」，后台改内容线上不刷新 | 写入时埋 `X-Cached-At` 时间戳，读取时按 ttl 校验新鲜度，过期即回源并覆盖 |

**已污染的旧缓存无需手动 purge**：静态资源走新 key 自动绕过；
API 旧条目没有时间戳烙印 → 判定过期 → 回源覆盖。

线上验证（新代码已生效）：

```
第1次: x-cached-at: 1793287394711  x-edge-cache: MISS
第2次: age: 1  x-cached-at: 1793287394711  x-edge-cache: HIT   ← 新鲜度校验生效
```

## 四、网络链路与域名排查

### 4.1 Brotli 与 HTTP/3：均已开启，无需配置

| 项目 | 证据 | 结论 |
|---|---|---|
| **Brotli** | 静态 HTML 与 JSON API 均返回 `content-encoding: br`（index.html 压缩后 9.8KB） | ✅ 已启用，Cloudflare 默认开启 |
| **HTTP/3 (QUIC)** | 响应头 `alt-svc: h3=":443"; ma=86400` | ✅ 已启用，由平台自动协商 |

> 补充说明：`/api/album/photos` 未显示 `content-encoding` 是因为响应体仅 146B，
> 低于 Cloudflare 的最小压缩阈值，属于正常取舍。

### 4.2 dpdns.org 存在**实锤的路由绕路**

同一台测试机（美西）同时访问两个域名，用 `cf-ray` 后缀判断实际落到的边缘节点：

| 指标 | `leiyihan.pages.dev` | `leiyihan.dpdns.org` |
|---|---|---|
| **cf-ray 边缘节点** | **LAX（洛杉矶）** ✅ 最近 | **LHR / AMS（伦敦 / 阿姆斯特丹）** ❌ 跨大西洋 |
| TCP 连接 | 0.477s | 0.536s |
| TLS 握手 | 0.757s | 0.771s |
| TTFB | 1.348s | 1.189s |
| **总计** | **1.355s** | **2.456s**（↑ 81%） |

两个域名都解析到 Cloudflare 的 IP 段，**差异不在 IP 归属，而在被分配到哪个边缘节点**。

**根因**：`dpdns.org` 是免费二级域名，其权威 DNS 由第三方托管，
Cloudflare 无法拿到准确的 EDNS Client Subnet（ECS）信息，
只能按递归 DNS 的位置猜测用户方位 —— 于是被导到了地球另一侧的欧洲节点。

### 4.3 具体优化建议（按优先级）

**①【根本解】注册自己的顶级域名，NS 迁到 Cloudflare**（推荐）

- DNS 由 Cloudflare 托管，ECS + anycast 精确调度，实测可把延迟砍半
- 顺带解锁 **Cloudflare Images**：本次相册缩略图就能自动生成，
  不再需要 `gen-album-thumbs.py` 手工补
- 解锁 CNAME 接入、Page Rules、WAF、Cache Rules 等
- 成本：`.com` 约 ¥60/年

**②【次选】确认 dpdns.org 的 DNS 是否支持 ECS**
多数免费二级域名服务不支持，若无解则只能走 ①。

**③【临时】让部分用户直连 `pages.dev`**
节点调度更准，但 `pages.dev` 在国内有被干扰的历史，需按用户群实测后再定。

| 相册图片拉取 | 2359ms | **715ms** | **↓ 70%** |
| 每页失败请求 | 1 个（620~1900ms） | **0 个** | **↓ 100%** |
| 静态资源边缘命中 | **0 / 12** | **7~8 / 12** | 从无到有 |

### 5.2 波动性指标（LCP）：单次采样不可靠，附归因

**先说结论**：本次为审计脚本新增了 **LCP 元素归因**能力
（只知道「LCP 3.4s」没有行动价值，必须知道**是谁钉住了首屏**）。归因结果：

| 页面 | FCP | LCP | 🎯 LCP 元素 | 归因 |
|---|---|---|---|---|
| 首页 | 1696ms | 1696ms | `div.nav-inner` | 文本 → 受 **TTFB** 主导 |
| 文章列表 | 1544ms | 1544ms | `h1.page-title` | 文本 → LCP ≈ FCP |
| 文章详情 | 5436ms | 6708ms | `p`（正文） | 文本 → 受**文章 API** 主导 |
| **相册** | 1604ms | 3580ms | **`img.lazy-img.loaded`** | **图片 → 缩略图优化正中靶心** |
| 网盘 | 2112ms | 2572ms | `p.m-desc` | 文本 |
| 小游戏 | 1564ms | 1564ms | `a#nav-logo.logo` | 文本 → LCP ≈ FCP |

**两点重要解读**：

1. **只有相册的 LCP 由图片承担**，其余 5 个页面都是文本元素。
   这意味着相册的缩略图优化**直接打在 LCP 元素上**；
   而其他页面的瓶颈是 **TTFB 与 CSS 到达时间**，跟图片/API 无关 ——
   这也解释了为什么「优化图片」不会让首页 LCP 下降。

2. **单次采样噪声极大**：同一页面多次采样，文章详情 TTFB 在 **412ms ~ 4121ms**
   之间跳动（10 倍），主要由第三方脚本（beacon + RUM，合计 800~2700ms）
   和跨境网络抖动造成。因此**不应以单次 LCP 论成败**，
   上表的「确定性收益」才是可信的优化证据。
