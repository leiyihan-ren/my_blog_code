# 开发与避坑指南

> 本指南收录本项目在全量压测、UI 打磨、无障碍整改与 v3.0 对外发布升级中**真实踩过并已修复**的坑，以及后续开发必须遵守的纪律。
> 每条标注：现象 → 根因 → 解法 → 涉及文件。新增代码前通读一遍可避开绝大多数夜间 debug。
>
> **章节导航**：一~四节为各技术域踩坑；第五节为早期测试方法论（历史存档）；**第七~九节为 v3.0 新增**（PWA 缓存更新机制 / CSP 配置注意事项 / API 代理维护手册）；第十节为现行测试体系速查。

## 一、Shell 与环境坑

### 1.1 pkill 会自杀（模式串匹配自身命令行）

```bash
# ❌ 危险：这条命令会 SIGTERM 自己（整行命令行含 "http.server 8601" 模式串）
pkill -f "http.server 8601"; python3 -m http.server 8601 …
```

**解法**：用端口杀进程，且与服务器启动**分成两条命令**：

```bash
fuser -k 8601/tcp 2>/dev/null   # 只杀占用端口的进程
# （下一条命令再启动服务器）
```

### 1.2 Playwright 截图的两种坐标参照系

- `page.screenshot({ clip })` 的 clip 用**文档坐标**（滚动后原点在文档顶部）
- `loc.boundingBox()` 返回**视口坐标**（相对当前视口）

两者混用 → 滚动后错位，截到错误区域（曾把 footer 的紫色回顶按钮当成文字背景，误报对比度 1.30:1）。

**解法**：元素级截图一律用 `loc.screenshot({ path })`，原生处理滚动，无需手算坐标。

### 1.3 视觉回归基线必须从对应 commit 重新导出

`git archive <commit> | tar -x -C /tmp/vis-orig` 得到的基线是**那个 commit 的快照**。拿过期基线与新版对比，会把中间已修复的差异重复报出来（曾一次误报 124 条 `#999` 修复差异）。

**纪律**：每个阶段用**上一阶段的 HEAD** 做基线重新导出，再跑回归。

## 二、CSS / UI 坑

### 2.1 同一个色值兼任背景与文字时，对比度不可兼得

`--primary: #4f46e5` 配白字（按钮背景）达 6.3:1，但直接用作暗色模式下的文字色只有 2.49~3.16:1。

**解法**：拆**文字专用令牌** `--primary-text`（亮 `#4f46e5` / 暗 `#818cf8`），73 处文字用途切换；背景/边框用途继续用 `--primary`（UI 组件 3:1 即可）。**新颜色上线前先问：它会被同时用作背景和文字吗？**

### 2.2 DOM 读取的对比度是区间，不是真值

渐变背景上 `getComputedStyle` 只能拿到 `background-image` 字符串，算不出真实对比度。

**解法**：像素级真值法——元素级截图 + PIL 取**非文字像素的众数颜色**（量化 8 级）作为文字背后主导背景。注意多区域元素（如 footer 内含回顶按钮）：取极端亮度值会把按钮像素误判为背景，众数法不受此影响。

### 2.3 标签语义变更（h2→h1、div→button）会静默丢失样式

`<h2>标题</h2>` 改成 `<h1>` 后，`.not-found h2 { color: … }` 选择器失配，标题回落到继承色——**JS 无报错、页面不崩，只是颜色弱化了**。

**解法**：标签更名必须全局搜索对应选择器同步修改；跑归一化视觉回归（路径剥离标签名）验证。同类：`div.tab → button.tab` 需补 `font-family:inherit; background:none; border:none` 继承外观。

### 2.4 弹性布局默认 `min-width:auto` 会撑破容器

flex 子项里的长文本/URL 不收缩，把整个头部挤出屏幕。

**解法**：`.header-inner > * { min-width: 0 }` + 全局 `overflow-wrap: break-word`。

### 2.5 改 `</div>` 的批量替换是重灾区

一次 tab 按钮化改造中，防护正则把 11+ 处无关的 `</div>` 误改为 `</button>`，HTML 结构静默损坏（浏览器容错渲染，肉眼难察）。

**解法与纪律**：
1. 批量结构替换**必须配对开闭标签一起替换**，拒绝"只换开标签"
2. 改完立即跑 HTML 栈平衡校验（Python `html.parser` 跳过 script 内容，比正则计数可靠）
3. 多行变更不要用 difflib 逐行对齐还原（replace 块不等长会 0 匹配），按内容模式定位修复

## 三、JavaScript 坑

### 3.1 原始计时器不在框架管辖内 = 幽灵回调

扫雷把 `setInterval` 注册在 `reset()`，重开叠加多个秒表；贪吃蛇重开双循环速度翻倍；Dpad 长按连发在切游戏后仍向废弃实例派发方向（"幽灵操作"）。

**解法**：`BaseGame` 统一登记 `after/every/raf/rafLoop/on`，pause/start/gameOver 自动 `clearTimers`，destroy 自动 `offAll`。**新增游戏一律用登记版，禁止裸调原生 API。**

### 3.2 innerHTML 全量重建会吞掉 CSS 动画

扫雷每次翻牌全量 `innerHTML` 重建棋盘，`.flip`/`.flag`/`.boom` 动画永远播不出来（新 DOM 直接就是终态）。

**解法**：一次性建格 + 原地更新 `class`/`textContent`，让过渡有"从旧态到新态"的过程。

### 3.3 切歌竞态：慢网络连点两首会互相覆盖

快速连点两首歌，第一个 `audio.src` 的 `onerror`/封面加载回调后置到达，把第二首的 UI 覆盖成第一首的状态。

**解法**：`loadToken` 自增令牌，每个异步回调先查 `myToken !== loadToken` 就 return。同理用于封面 `img.onerror`。

### 3.4 连续加载失败会无限自动切歌

某首歌 URL 失效 → `error` 事件 → 自动切下一首 → 也失效 → 无限循环，用户永远被偷走播放控制权。

**解法**：`consecutiveErrors` 计数，达阈值停止自动切换；`playing` 事件归零。手动切歌取消未触发的 `pendingSwitch`。

### 3.5 事件监听互相覆盖：`onkeydown =` 是独占的

游戏早期劫持 `document.onkeydown = …`，会把播放器的键盘快捷键整条覆盖掉（后者赋不上值）。

**解法**：一律 `addEventListener`；播放器再叠一级让位链——游戏运行中（`GameCore.isGameRunning()`）、灯箱打开（`.lightbox.active`）、焦点在表单/按钮、组合键，四级全不命中才响应。

### 3.6 点击后的焦点残留：空格/回车会二次触发

鼠标点过「开始」后按钮保持 focus，用户按空格翻页/暂停时又触发一次按钮。

**解法**：舞台按钮统一 `blur(fn)` 包装——执行后 `e.currentTarget.blur()`。

### 3.7 对象存不了纯数字键的有序表

`{ "2048": …, snake: … }` 枚举时 `"2048"` 被排到最前，游戏卡片与排行榜顺序错乱。

**解法**：注册表用 `Map`。

### 3.8 escapeHtml 不转义引号，属性上下文会注入

`<div data-id="${escapeHtml(x)}">`，若 `x` 含 `"` 可闭合属性注入 `onmouseover` 等。

**解法**：`escapeAttr`（escapeHtml + 替换引号）；**规则：文本用 escapeHtml，属性一律 escapeAttr。**

### 3.9 隐私模式下 localStorage 抛错会中断整页脚本

`localStorage.setItem` 在隐私模式/存储禁用时抛 `SecurityError`，一条未捕获异常会让后面全部初始化代码不执行。

**解法**：全项目统一 `safeStorage` 包裹（admin/music-player/game-core 三处各自定义，刻意不共享以保组件独立）。

## 四、后端 / Worker 坑

### 4.1 KV 键名散落字符串 = 备份清理双漏洞

键名硬编码在业务代码里时，`deletePrefix` 清理与备份导出容易漏。

**解法**：全部收进 `KEYS` 常量（`site/posts/messages/comments_<id>/gh_*/…`），新存储先加常量。

### 4.2 公开写端点不限流 = 被刷穿

留言/评论/点赞/提交分数四条公开写路径，任何一条漏了 IP 级限流（冷却 + 每小时上限）都会被脚本刷爆 KV 写入配额。

**解法**：新增公开写端点必须在 `handlers` 里补齐限流三件套（cooldown 键 + hour 键 + 锁定键），并在 ROUTES 表标注 `needBody`。

### 4.3 路径参数可能带畸形百分号编码

`/api/post/%ZZ` 直接 `decodeURIComponent` 会抛异常导致 500。

**解法**：`matchRoute` 里 try/catch，解码失败置 `null` 交给下游校验返回 400。

### 4.4 双内容源的「删除复活」问题

后台删掉一条 GitHub 同步来的文章，仓库不变 → 下次合并它又出现。

**解法**：`deleted_ids` 墓碑键（`{ posts:[], music:[], timeline:[] }`），删除仓库来源条目时记 id，合并层据此隐藏。导入备份会连带墓碑，删本地内容前先想清楚墓碑语义。

### 4.5 备份导入必须校验形状

用户导入一个 `{}` 或数组，全量覆盖会清空站点。

**解法**：`importBackup` 校验 `payload.data` 存在且为对象；前端同样预检并 confirm 二次警告。

### 4.6 认证模型：token = 密码本身

后台用 `Authorization: Bearer <管理密码>`，sessionStorage 生命周期（关标签页即失效）。不要把它升级成"长效 token"——那等于把密码落盘。旧版本曾写 localStorage，现有代码做了一次性迁移清理（`tokenStorage.remove`）。

## 七、PWA 缓存更新机制（防止用户永远看旧页面）

> 涉及文件：`sw.js`（缓存策略 + 版本控制）、`common.js` 的 `initPwa()`（注册 + 自动刷新）、
> `_worker.js` 的 `staticCacheControl()`（sw.js/manifest 的 HTTP 缓存头）。
> 测试锚点：`tests/step1-pwa-verify.mjs` 的 P6/P7/P8 场景。

### 7.1 四层防线（缺一层就会漏旧页面给用户）

```
① sw.js 本身不被长缓存   max-age=0, must-revalidate（_worker.js）
        ↓ 浏览器每次访问都重新验证 SW 脚本，能发现"有新版本"
② install 即接管          skipWaiting()，不等旧 SW 自然退休
        ↓
③ activate 清理旧缓存      删除所有 my-blog-static-*（保留当前版本号）
        ↓
④ 页面自动刷新一次         controllerchange 监听，仅「旧→新」接管时 reload()
```

第 ① 层是**咽喉**：若 sw.js 被浏览器 HTTP 长缓存，后面三层根本没有触发机会——
用户浏览器里的 SW 永远是旧版本，`CACHE_VERSION` 加多少次都没用。

### 7.2 缓存策略总览（sw.js）

| 请求类型 | 策略 | 理由 |
|---------|------|------|
| HTML 导航 | network-first，断网回退缓存 | 内容随时变，在线必须最新；断网才允许旧 |
| 同源静态资源（JS/CSS/图标） | stale-while-revalidate | 秒开 + 后台静默更新，下次即最新 |
| `/api/*` GET | stale-while-revalidate | 同上；POST 写操作一律不拦截 |
| Range/206 音频 | 缓存完整版后按 Range 切片返回 | 音频离线可播、拖动进度条可用 |

### 7.3 发布纪律

1. **每次发布 `CACHE_VERSION` 必须 +1**（sw.js 头部唯一常量，漏改 = 用户停留在旧缓存）；
2. 文件名无 hash 后缀（`common.js` 而非 `common.a3f2.js`），所以 JS/CSS 只给 1 小时短缓存，
   上传新版本后最长 1 小时 + 一次后台刷新即全量生效；
3. 发布后跑 `node tests/step1-pwa-verify.mjs`，P6/P7/P8 三组必须全绿才算发布成功。

### 7.4 踩坑记录

**坑 1：Range 请求的 `cache.put` key 不能带 Range 头。**
规范要求带 `Range` 头的请求只能配 206 响应，`cache.put(rangeReq, fullResp)` 直接抛
`TypeError`。解法：用无 Range 头的同 URL `Request` 作 key 存完整版，后续带 Range 的
`match` 仍能命中（Cache API 的 key 只看 URL）。

**坑 2：SW 的 `fetch(req)` 会命中浏览器 HTTP 磁盘缓存，兜底层触发条件比直觉严格。**
worker 给公共 GET 接口设 `Cache-Control: public, max-age=ttl, stale-while-revalidate`，
SW 即使 Cache API 里没有，`fetch(req)` 也可能从 HTTP 磁盘缓存拿到陈旧 200——
这是**正确的生产行为**（边缘缓存 + 浏览器缓存双层），但意味着前端的
localStorage 兜底（如相册 `album_photos_v3`）只在「SW 缓存 + HTTP 缓存全失效」时才触发。
测试该路径必须用全新 browser context + 预置 localStorage 种子，不能靠关服务器复现。

**坑 3：SWR 离线竞态。**
离线刷新时 cache hit 触发的后台重新验证，会在恢复联网后完成 `cache.put`，
可能与随后的缓存清理竞态。`trimCache` 按插入序淘汰 + `activate` 只删
`my-blog-static-*` 前缀（不碰 `my-blog-runtime-v1`）来控制影响面。

**坑 4：首次注册不能触发自动刷新。**
`controllerchange` 在首次注册时也会触发，若无条件 `reload()` 用户首访就莫名刷一次。
解法：注册前记 `hadController`，仅当页面**本来就有** SW 控制器（即旧→新接管）才刷新，
且 `reloading` 哨兵防循环。

## 八、CSP 配置注意事项

> 涉及文件：`_worker.js` 的 `CSP_POLICY` 常量 + `addStaticSecurityHeaders()`（静态 HTML）
> + `buildHeaders()`（API 响应）。
> 测试锚点：`tests/step3-seo-csp.mjs` 的 C1/C2 组。

### 8.1 单点定义，两处生效

`CSP_POLICY` 是全项目**唯一** CSP 定义，两条路径强制附加，无漏网响应：

```
静态 HTML：env.ASSETS.fetch → addStaticSecurityHeaders()  → 仅 text/html 加 CSP
API 响应：buildHeaders()                                  → 所有 JSON 统一加 CSP
```

**纪律**：新增响应路径必须过这两个函数之一；禁止在单个 handler 里手写 CSP 头
（必然漏，且改策略时要全局搜）。

### 8.2 当前策略逐条说明

```
default-src 'self';
script-src  'self' 'unsafe-inline' https://static.cloudflareinsights.com;
style-src   'self' 'unsafe-inline';
img-src     'self' data: https:;
font-src    'self' data: https:;
media-src   https: data:;
connect-src 'self' https://static.cloudflareinsights.com https://cloudflareinsights.com;
frame-src 'none'; object-src 'none'; base-uri 'none';
form-action 'self'; worker-src 'self';
frame-ancestors 'none'; manifest-src 'self'; upgrade-insecure-requests;
```

| 指令 | 为什么这样配 |
|------|-------------|
| `script-src 'unsafe-inline'` | 项目大量内联脚本（防闪主题脚本、页面初始化），**刻意接受的取舍**：用 nonce/hash 改造工作量巨大且易漏，本站无用户输入直达 innerHTML 的执行路径（留言板走 textContent + 服务端净化），风险可控 |
| `worker-src 'self'` | **PWA 咽喉**：不放行同源，浏览器会以 CSP 为由拒绝注册 `sw.js`，离线能力直接失效。曾在此漏配，P6 测试抓出 |
| `img-src https:` | 相册图片走多镜像 CDN（jsDelivr/raw/statically），必须放行 https 外域 |
| `frame-ancestors 'none'` | 禁任何站点 iframe 嵌入本站（防点击劫持），与 `X-Frame-Options: DENY` 新旧双保险 |
| `upgrade-insecure-requests` | http 子资源自动升 https；localhost 开发环境浏览器自动豁免 |

### 8.3 改动纪律

1. 动 `CSP_POLICY` 后必跑 `node tests/step3-seo-csp.mjs`（静态头 + API 头 + 9 页面无 CSP 违规报错）；
2. 新增外域资源（新 CDN、统计脚本）→ 先确认加哪个指令，**宁紧勿松**；

## 九、API 代理维护手册（/api/github/*）

> 涉及文件：`_worker.js` 的 `ghFetchWithFallback()`、`buildImageMirrors()`、
> `resolveGithubAssetUrl()`、`API_CACHE_TTL`；前端 `album.html` / `music-player.js` / `post.html`。
> 铁律：**前端禁直连 GitHub 域名**，一律走 `/api/github/*` 同源代理。

### 9.1 为什么必须代理（三条理由）

1. **Token 不暴露**：worker 侧持有 GitHub Token（私有仓库/提额），前端只见同源路径；
2. **弱网可达**：经 Cloudflare 边缘缓存，受限网络下不依赖浏览器直连 raw.githubusercontent.com；
3. **镜像自治**：代理故障时前端还有 CDN 镜像兜底链，单点故障不白屏。

### 9.2 两条代理通道

| 路径 | 用途 | 上游 |
|------|------|------|
| `/api/github/raw/<repo>/<branch>/<path>` | 图片/音频/任意文件字节流 | raw.githubusercontent.com（边缘缓存 1 天） |
| `/api/github/list/<repo>/<branch>/<dir>` 等 | 目录列表（曲目/照片扫描） | api.github.com / jsDelivr data API |

### 9.3 四级镜像链（前端加载图片时逐个切换）

```
/api/github/raw/*（同源代理，Cloudflare 边缘缓存）
  → cdn.jsdelivr.net（CDN，独立配额）
  → raw.githubusercontent.com（官方）
  → cdn.statically.io（兜底）
```

`buildImageMirrors()` 生成顺序数组，前端 `loadImgWithFallback` 逐个尝试，
全部失败派发 `imgallfailed` 呈现失败态。worker 侧 `ghFetchWithFallback(kind, repo, path, branch, useCdn)`
同理：`useCdn` 开启时 jsDelivr 优先（省官方配额），关闭时官方优先；检测到
`X-RateLimit-Remaining` 过低会自动剔除 github 源让 CDN 顶上。

### 9.4 三层缓存（边缘 → SW → localStorage）

```
① worker 边缘缓存   API_CACHE_TTL 表（如 /api/album/photos 60s）+ stale-while-revalidate
② SW 运行时缓存     my-blog-runtime-v1，stale-while-revalidate，80 条上限按插入序淘汰
③ localStorage      album_photos_v3 / 歌单快照，前两层全失效时的最后防线
```

**坑（已记录在 7.4 坑 2）**：① 的 HTTP 缓存会被 SW 的 `fetch(req)` 命中，
所以 ③ 的触发条件比预想严格——测试时必须用全新 context + 预置种子。

### 9.5 新增代理/数据接口的维护步骤

1. 路由进 `ROUTES` 表，公开写端点必须补齐限流三件套（cooldown + hour + 锁定键）；
2. **决定是否进 `API_CACHE_TTL`**：只缓存 GET 且无需管理权限的接口；带 `Authorization` 的
   一律不缓存；`like/view/comments` 等计数与 IP 去重接口**不进表**（避免计数失真）；
3. 管理端写操作成功后会清空 `API_CACHE_TTL` 全部键（数据实时性）；
4. 前端只写 `/api/...` 相对路径，镜像链交 `buildImageMirrors` 生成，禁止手拼外域 URL；
5. 跑对应测试套件（相册/歌单场景）确认代理、缓存、兜底三层行为。

## 十一、GitHub 云盘架构（文件管理器 / drive.html）

> v5.0 新增（2026-10-23）；v6.0 扩展大文件分片协议（2026-10-24，见 11.8）。
> 章节导航同步更新：第七~十一节为 v3.0/v5.0 新增。

### 11.1 架构总览

```
浏览器 drive.html
  │  fetch /api/drive/* （头 x-drive-pin）
  ▼
Cloudflare Worker（_worker.js 7.7 区）
  │  PIN 校验 → 路径净化 → 大小兜底
  │  ghApiWrite / ghApiRequest（Worker 内注入 GITHUB_TOKEN）
  ▼
GitHub Contents API（leiyihan-ren/Blog 仓，drive/ 目录）

v6.0 大文件（>8MB）追加分片协议：
  drive/<小文件>                  ≤8MB 单次 PUT（原路径）
  drive/.m-<uploadId>.json        manifest（扁平化顶层，见 11.8 坑 1）
  drive/.parts/<uploadId>/part-NNNNN   5MB 分片，每片一个独立 commit
```

| 端点 | 方法 | 作用 | SHA 处理 |
|---|---|---|---|
| `/api/drive/list?path=drive` | GET | 目录列表（含每文件 sha、大小、上传时间；manifest 合并为大文件条目） | — |
| `/api/drive/upload` | POST | 新建/覆盖上传（**仅 ≤8MB**） | **后端自动判别**：GET 探测存在 → 存在则带 sha 覆盖，不存在则不带 sha 新建 |
| `/api/drive/update` | PUT | 更新（强制已存在） | 后端先 GET，拿不到 sha 返回 404 |
| `/api/drive/delete` | DELETE | 删除（manifest 删除 = 逐片删 + 删清单，带 409 自愈） | 后端先 GET 拿 sha，再 DELETE |
| `/api/drive/upload/status` | GET | 分片断点查询（已落库分片序号） | — |
| `/api/drive/upload/part` | POST | 单片上传（≤5MB，Base64；已存在则带 sha 覆盖，幂等） | 后端 GET 探测后代取 |
| `/api/drive/upload/finish` | POST | 校验分片齐全后写 manifest | 后端判别（同 upload） |
| `/api/github/raw/<repo>/<branch>/<path>` | GET | 下载（小文件直链；大文件前端拉 manifest + 分片重组） | — |

**Token 全程不出 Worker**：前端只持 PIN 口令（`x-drive-pin` 头），GitHub Token 仅在
`ghHeaders()` 内注入 Authorization。`/api/github/api/` 的写方法透传（POST/PUT/DELETE/PATCH）
同样要求 PIN，防止代理被匿名滥用。

### 11.2 Token 读写权限配置（v5.0 实测）

管理 GitHub Secrets 需 **Secrets: Read and write**；触发 `workflow_dispatch` 需独立的
**Actions: Read and write**（与 Workflows 权限是两个独立项——Workflows 只管改工作流文件，
不管运行）；读写仓库文件需 **Contents: Read and write**。fine-grained token 现支持
**创建后直接编辑权限、即时生效**，无需换 token。

云盘写入目标仓 `leiyihan-ren/Blog`（数据仓，与相册/文章同源）；代码仓为
`leiyihan-ren/my_blog_code`，两者 token 范围不同，勿混淆。

### 11.3 SHA 获取逻辑（GitHub Contents API 硬性要求）

- **新建文件**：PUT 不带 `sha`；
- **更新已有文件**：PUT 必须带当前 `sha`，否则 409；
- **删除文件**：DELETE body 必须带 `sha`。

本项目的策略是**后端静默代取**：前端 upload/update/delete 都不传 sha，Worker 先
`GET /repos/:repo/contents/<path>?ref=main` 拿元数据，再决定是否带 sha 发起写请求。
好处：前端逻辑简单、无「前端缓存 sha 过期」竞态；代价：每次写多一次 GET 调用
（5000 次/小时配额下可忽略）。

### 11.4 大小限制：8MB 直传阈值 / 2GB 分片上限（v6.0 起）

- **≤8MB**：Contents API 单次 PUT 原路径。8MB → Base64 约 10.7MB + JSON 外壳，
  低于 CF 免费版 100MB 请求体上限，Worker 128MB 内存无压力；
- **>8MB**：走分片协议（见 11.8），**单文件产品上限 2GB**。依据：仓库软限 5GB；
  Contents API 配额 5000 次/h（2GB = 410 片可控）；单片 5MB → Base64 6.7MB，
  请求体上限 8.5MB（`CONFIG.drive.maxPartBodyBytes`）远低于 CF 限制；
- v5.0 时期的 10MB 直传已降级为 8MB 阈值——超过即引导分片，不再硬拒。

注意：`readJson()` 有 100KB 通用上限（`CONFIG.request.maxBodyBytes`），云盘必须走
专用 `readDriveJson()` / `readDrivePartJson()`，否则大文件 body 被静默丢弃返回 null。

### 11.5 PIN 访问口令

- 口令校验在 **Worker 端**：`env.DRIVE_PIN || CONFIG.drive.fallbackPin`（默认 `8866` 仅兜底，
  生产应在 CF Pages 环境变量配置）；
- 前端进入页面即 prompt，存 `sessionStorage`，此后所有 `/api/drive/*` 请求带
  `x-drive-pin` 头；401 且错误信息含「口令」时自动清会话并重新弹窗；
- 纯前端 prompt 不设防（源码可见），真正的边界是 Worker 校验——未配 `DRIVE_PIN` 时
  默认口令也在 Worker 内，仍强于裸奔，但**上线后应立即配置环境变量**。

### 11.6 踩坑记录（v5.0 实测）

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | 删除/上传成功后列表不刷新，1 秒后刷新又正常 | **Service Worker 的 `/api/*` SWR 缓存**：`sw.js` 对同源 `/api/*` GET 走 stale-while-revalidate，先返回旧缓存、后台才更新 | `sw.js` fetch handler 对 `/api/drive/` 直传网络（1.5 分支）；Worker 侧所有 drive 响应加 `Cache-Control: no-store`（`driveOk`/`driveErr`）双保险 |
| 2 | 本地端到端测试写操作全部 400「参数缺失」 | 测试 API server 构造 `new Request()` 时**漏传 body**（读路径测试从未暴露） | `startApi` 先 `readBody(req)` 再传入 Request |
| 3 | mock 文件列表为空但 API 200 | mock 数据漏了 `type: "file"` 字段，被 Worker 的 `.filter(it => it.type === "file")` 全部过滤 | 补全 mock 数据结构 |
| 4 | DELETE 请求 405 | `dispatchApi` 原仅放行 GET/POST，且代理拦截在方法检查之后 | 将 `/api/github/`、`/api/drive/` 拦截**提前**到方法检查之前，代理自身管理方法 |
| 5 | 批量替换 `return err(` 误伤包装函数自身 | sed/python 范围替换把 `driveErr` 定义体内的调用也改成自身 → 无限递归 | 定义体单独修正；今后批量替换必须排除目标函数定义区 |

### 11.8 大文件分片协议（v6.0，>8MB）

**为什么分片**：GitHub Contents API 单文件绝对上限 100MB，且 Base64 膨胀 33%、
Worker 30s 写超时——8MB 以上直传必挂。**为什么浏览器端重组下载**：GitHub
没有多 blob 拼接 API（Blob API 只能单 contents 端点创建），下载只能在
前端拉 manifest → 并发 4 路拉分片 raw → `new Blob(parts)` 重组，Blob 由
浏览器磁盘承载，不全量进 JS 堆（2GB 文件也不 OOM）。

**上传协议**（前端 `services/uploadService.js` ↔ Worker `CONFIG.drive`）：

```
status   GET  /api/drive/upload/status?uploadId=…   → 已落库分片序号（断点）
part     POST /api/drive/upload/part  {uploadId,index,content}  单片独立 commit
finish   POST /api/drive/upload/finish {uploadId,name,size,total}  校验后写 manifest
```

- 分片大小 5MB（Base64 后 6.7MB，低于 `maxPartBodyBytes` 8.5MB）；
- 串行上传（同时只传 1 片，峰值内存 5MB）；文件级并发 ≤2；
- 单片失败指数退避 1s/2s/4s 自动重试 3 次；耗尽后**不中断后续片**，
  收集失败序号，全部跑完统一进失败态——「继续上传」只补失败片（断点续传）；
- 单文件产品上限 2GB（仓库软限 5GB × API 配额 5000 次/h 的稳妥值）。

**踩坑记录（v6.0 实测）**：

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | 大文件 manifest 写了 `drive/.parts/<id>/manifest.json`，列表页不显示 | Contents API 的 list **只返回一级目录项**，二级文件不出现 | manifest 扁平化到 `drive/.m-<id>.json` 顶层（见 11.1 图） |
| 2 | 下载点击后 Blob 大小 0，控制台 ReferenceError | `encodePathSegments` 只在 `_worker.js` 定义，前端调用即未定义 | 前端补同名工具函数；新增「提取 script 块静态扫描调用 vs 声明」防再犯 |
| 3 | 连续写入后删除报 409 SHA 冲突 | GitHub 读副本滞后（最终一致性），目录列表 sha 已过期 | Worker `ghDeleteContents` 刷新 sha 重删，**最多 3 次有界重试**，3 次后友好报错 |
| 4 | 压测日志写「10MB → 3 片」实际只传 2 片 | 文案复制 12MB 场景；`ceil(10MB/5MB)=2` 计算本就正确 | 修正日志文案（非产品缺陷，避免误导排障） |
| 5 | `git push ... \| tail -3 && echo OK` 推送失败也打印 OK | 管道退出码是 tail 的 | 推送命令禁用管道，直接判 `$?` |
| 6 | 断言「删除恰好 N 次」偶发失败 | mock 只记录成功删除，409 那次未计数 | mock 补记 `del409` 日志；断言改「409 一次 + 重删成功一次」 |

### 12.2 页面重写层（URL 零破坏的实现）

```
浏览器 /drive.html ──► Worker 重写 ──► ASSETS /pages/drive.html ──► 200（URL 不变）
```

页面内所有本地引用一律**根绝对路径**（`/styles/common.css`），与物理目录

## 十三、v7.1 网盘状态机重构（2026-10-24）

### 13.1 状态机模型（UI 只渲染，流转全部归 uploadService）

v7.0 把引擎剥离出页面后，v7.1 把**状态流转也完全收拢到服务层**：
`UploadService.STATE` 是唯一枚举源，页面 `renderQueue()` 只读 `tasks()`
画界面，不再出现任何状态字符串字面量。

```
                ┌──────────────────────────────────────────────┐
                │              ACTIVE_STATES（占并发槽）          │
                ▼                                              │
 pending ──► reading ──► uploading ──► finishing ──► done      │（小文件直传）
     │                                                          │
     ├─► checking ─► uploading ──► finishing ──► done           │（大文件分片）
     │                                                          │
     ├─ pause() ─► paused ── resume() ─► pending（断点续传）      │
     │                                                          │
     └─ 重试耗尽 ─► failed ── retry() / online 自动恢复 ─► pending│
                └──────────────────────────────────────────────┘
 任意活动态 ── cancel() ─► canceled（出队；服务端已传分片保留供续传）
```

| 状态 | 占并发槽 | UI 按钮 | 说明 |
|---|---|---|---|
| pending | ✅ | 暂停/取消 | 排队中 |
| reading / checking | ✅ | 暂停/取消 | 小文件整读 / 分片断点查询 |
| uploading | ✅ | 暂停/取消 | 传输中 |
| finishing | ✅ | 暂停/取消 | 写 manifest 收尾 |
| paused | ❌ | 恢复/取消 | 用户主动暂停，断点保留 |
| failed | ❌ | 继续上传/取消 | 重试耗尽，可手动或自动恢复 |
| done | ❌ | — | 成功终态 |
| canceled | — | — | 已出队 |

### 13.2 暂停/恢复/取消的实现要点

1. **XHR abort 登记**：`xhrUpload(..., task)` 把 `task._abort = () => xhr.abort()`
   挂到任务上；`pause/cancel` 先置状态再调 `_abort()`，在途请求立即掐断。
2. **PAUSE_SENTINEL 分流**：abort 后 `onabort` reject 哨兵对象；各层 catch 一律
   **先判 `task.status` 再处理**——paused/canceled 静默收场，绝不误报 failed，
   绝不弹错误 toast。退避等待期间也有 `throwIfPaused` 守卫，杜绝「暂停了还在传」。
3. **在途落库语义（重要认知）**：客户端 abort 不等于服务端没收到。在途 PUT
   服务端可能照常落库（≤+1 片）——这是 HTTP 语义，不是 bug；恢复时断点
   status 查询会跳过已落库片，**绝不重复传**（step11 S1e/S5b 断言守护）。
4. **恢复即重试**：`resume()` 复用 `retryTask()` 语义（paused → pending），
   分片模式经 status 查询只补缺失片；直传模式整文件覆盖写（幂等）。

### 13.3 并发 2→3 与断网重连

- `MAX_CONCURRENT = 3`（v7.1 从 2 上调）：step9 V5b 断言峰值 ≤3 且 V5c 断言
  ≥2（防退化为串行）；step11 S4 断言峰值 =3 且并发中 UI 主线程响应 <2s。
- **断点 status 查询重试（v7.1 补缺口）**：弱网/断网从入队就开始时，首个请求
  往往就是 status GET——v7.0 它无重试会直接误判失败。v7.1 补上与单片同款的
  指数退避（1s/2s/4s ×3），GET 幂等零副作用。
- **online 事件自动恢复**：`window.online` 时把所有 failed 任务自动 resume
  并 toast 告知。断网期间任务不丢、不误删，重连即续跑——step11 S2b 全链断言
  （入队即断网 → 退避 → 耗尽 failed → online → 自动补齐 0/1/2 片 → done）。

### 13.4 beforeunload 防误关

drive.html 监听 `beforeunload`，仅当 `UploadService.isBusy()`（有活动任务）时
`preventDefault()` 弹确认框。暂停/失败/完成态不拦——用户已明确知道状态，
无需骚扰。step11 S3 用 `dispatchEvent(new Event("beforeunload", {cancelable:true}))`
断言 `defaultPrevented`，S6 验证暂停态 `runBeforeUnload` 关闭不卡死。
