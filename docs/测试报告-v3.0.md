## 二、用户重点关切：PWA 离线缓存是否导致新代码不更新

这是本次回归的核心风险点，由 `step1-pwa-verify.mjs` 的 **P6 / P7 / P8** 三组场景覆盖，全部通过：

### P6 SW 版本控制（新版本发布后用户不停留旧页面）

| 断言 | 结果 |
|------|------|
| 新版本缓存 `my-blog-static-v3.0.2` 已建立且旧版本 `v3.0.1` 已清理 | ✅ |
| 页面最终由新 SW 控制（自动刷新生效） | ✅ |
| 刷新后仍稳定受控（无刷新循环） | ✅ |

**防护机制（四层，详见《开发与避坑指南》第七章）：**

1. `sw.js` 头部唯一常量 `CACHE_VERSION`，每次发布必须 +1；
2. `install` 后立即 `skipWaiting()` + `activate` 删除所有旧版本 `my-blog-static-*` 缓存；
3. 页面侧 `controllerchange` 监听：仅当「旧 SW → 新 SW」接管时自动 `reload()` 一次（首次注册不触发，避免首访莫名刷新）；
4. `_worker.js` 对 `sw.js` / `manifest.json` 响应 `max-age=0, must-revalidate`——浏览器每次都会重新验证 SW 脚本本身，**这是整条链路的咽喉**：若 sw.js 被 HTTP 长缓存，后续全部机制都发现不了新版本。

### P7 HTML 内容新鲜度（网络优先）

HTML 导航请求走 **network-first**：在线刷新立即拿到最新 HTML，不被 SW 旧缓存卡住；断网才回退缓存。后台改完文章刷新即可见。

### P8 响应头

`sw.js` 与 `manifest.json` 均 `max-age=0, must-revalidate`；HTML 带 CSP 且放行 `worker-src 'self'`（否则 SW 注册会被 CSP 拦截，PWA 直接失效）；nosniff / X-Frame-Options 等安全头保留。

## 四、测试基础设施

### 目录结构

```
tests/
├── _helpers.mjs               # 共享：ROOT 解析 + worker 动态导入 + Chromium 启动参数

├── step3-seo-csp.mjs          # SEO/CSP 52 项
├── step3-ui-stress.mjs        # 压测 27 项
├── step4-a11y-audit.mjs       # a11y 165 项
├── step4-lightbox-trap.mjs    # 灯箱 7 项
└── step5-common-verify.mjs    # 交互回归 102 项
```

### 可移植性设计（无任何硬编码路径）

- `tests/_helpers.mjs` 从 `import.meta.url` 推导仓库根目录，动态导入 `_worker.js`；
- Chromium 可执行文件经 `CHROMIUM_PATH` 环境变量注入，未设置时用 Playwright 自带浏览器；
- Playwright 走 `package.json` devDependency 安装，全局/本地均可解析。

### 架构模式

| 套件类型 | 链路 |
|---------|------|
| PWA / 歌单 / 相册 | 浏览器 → 自起静态服务器(8899) → /api 转发内嵌 worker → mock GitHub 上游，**SW 完整参与** |
| 压测 / a11y / 灯箱 | 浏览器 → 自起静态服务器(8899) + `/api` 经 `page.route` 拦截转发内嵌 worker(8602) → mock GitHub |
| SEO/CSP | 源码级静态分析 + mock ASSETS worker 层 + Playwright DOM 级 |
| common 回归 | 浏览器 → 自起静态服务器(8899)，验证主题/菜单/滚动交互 |

所有 mock 上游（GitHub API / raw / CDN 镜像）均为测试内自建 HTTP 服务，**不访问外网**，CI 环境可确定性复现。

## 五、CI 自动化（GitHub Actions）

`.github/workflows/test.yml`：push / PR 到 main 触发 →

1. `actions/checkout@v4`
2. `setup-node@v4`（Node 22，npm 缓存）
3. `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm ci`（跳过下载，版本精确锁定）
4. `npx playwright install --with-deps chromium`（安装与 playwright 版本匹配的浏览器）
5. `npm test` → 任一断言失败即 job 失败

本地复现 CI 行为：

```bash
PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm ci
npx playwright install chromium        # 或设置 CHROMIUM_PATH 复用系统 Chromium
npm test
```

## 七、已知边界（非缺陷，刻意设计）

1. **接口 502 兜底的触发条件比直觉严格**：worker 对公共 GET 设 `Cache-Control: public, max-age=ttl, stale-while-revalidate`，SW 的 `fetch(req)` 会命中浏览器 HTTP 磁盘缓存拿到陈旧 200（这是正确的生产行为）。localStorage 兜底层（album v3）只在「SW 缓存 + HTTP 缓存全失效」时触发。测试用全新 browser context + 预置 localStorage 种子确定性复现该路径。
2. **测试端口固定**（8899 静态 / 8602 API / 8612+ 场景 API）：套件必须**顺序执行**（run-all.mjs 已保证），并行会端口冲突。
3. 旧版 `album-verify` / `network-proxy-verify` 测试基于旧 API 形态（`?ref=main`、旧函数名、KV 跨请求假设），已判定退役，场景被相册 64 项 + 灯箱 7 项 + a11y 165 项全覆盖。
