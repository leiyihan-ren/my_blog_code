# 线上全页面诊断与优化对比报告（v8.1）

- 站点：`https://leiyihan.pages.dev`
- 采集工具：`tests/_perf-audit.mjs`（Playwright 真实访问，`waitUntil=load` + 静置 4s，逐请求计时）
- 采集轮次：优化前 2 轮、优化后 3 轮

---

## 一、优化前基线（实测）

| 页面 | TTFB | FCP | LCP | LOAD | API 数 | 静态边缘命中 |
|---|---|---|---|---|---|---|
| 首页 | 757ms | 1532ms | 1532ms | 2851ms | 5 | **0/12** |
| 文章列表 | 780ms | 1464ms | 1464ms | 2463ms | 3 | **0/11** |
| 文章详情 | 1792ms | 2792ms | 3784ms | 4536ms | 6 | **0/11** |
| 相册 | 856ms | 1268ms | **4256ms** | 1338ms | 5 | **0/12** |
| 网盘 | 571ms | 1008ms | 1352ms | 2320ms | 2 | **0/9** |
| 小游戏 | 504ms | 1112ms | 1112ms | 2062ms | 3 | **0/12** |

三个致命发现：

1. **静态资源边缘缓存命中 0/12** —— 12 个 CSS/JS/图片每次全部回源。
2. **`/api/*` 从未命中边缘缓存** —— 响应虽带 `public, max-age=N`，但实测无 `cf-cache-status`
   （旁证：同为 `/api/` 下的 `.jpg` raw 代理却带 `HIT`）。
3. **重复请求** —— 相册同一张 raw 图请求 2 次、网盘 `/api/drive/list` 请求 2 次。

---

## 二、根因（不是"GitHub 慢"这么简单）

| # | 现象 | 真实根因 |
|---|---|---|
| 1 | 静态资源零缓存 | Pages 上游给静态资源默认下发 `no-store` / `max-age=0, must-revalidate`；Worker 原逻辑「上游有 Cache-Control 就不覆盖」→ **缓存策略从未生效** |
| 2 | `/api/*` 零缓存 | **Cloudflare 默认只按扩展名缓存静态内容**，`/api/posts` 这类无扩展名路径不在默认缓存列表内；光设 `Cache-Control` 头无效，必须用 Cache API 显式写入 |
| 3 | 首屏 500~800ms | 上述两者叠加：每个页面 11~12 个静态资源 + 3~6 个 API 全部回源 |
| 4 | 慢上游拖死整页 | `github.timeoutMs` 为 8000ms，一个劣化上游可独占用户 8 秒；前端 `BlogApi` 默认超时 12s |
| 5 | 重复请求 | 前端无并发去重：相册 `<img>` 与懒加载各触发一次，网盘初始化与解锁各调一次 |

## 三、已落地的优化

### Worker 层（`_worker.js`）

| 项 | 改动 |
|---|---|
| 静态缓存强制化 | 去掉「不覆盖上游」判断，按类型分级下发：HTML `s-maxage=300`+SWR / CSS·JS `s-maxage=1d` / 图片·字体 `s-maxage=7d` |
| 静态资源入 Cache API | GET 静态资源显式 `cache.put`，命中即零回源（HTML 不入库，发版即时性优先） |
| API 边缘缓存 + 单飞 | 新增 `dispatchApiCached()`：只读 GET 走 Cache API，**同 isolate 内并发只放行一个回源** |
| 请求熔断 | `github.timeoutMs` 8000 → **3000ms**（配合既有换源 + 重试） |
| 速率限制 | 极简限流 60s/120 次；**仅对带 `cf-connecting-ip` 的真实边缘请求生效**，本地/测试环境放行不误伤 |

### 前端层（`services/request.js` + 首页）

| 项 | 改动 |
|---|---|
| 超时分层 | 读接口 **3s 熔断** / 写接口 12s（原统一 12s，把上游延迟直接转嫁用户） |
| 并发去重 | 同 URL 的 GET 只发一次，其余复用同一 Promise |
| 离线降级 | `cacheKey` + `onFallback`：失败自动用本地缓存渲染并回调页面提示，不白屏 |
| 首页接入 | 站点/文章/统计/热门四路并行，**任一失败只影响该区块**；命中缓存时顶部提示「离线数据」 |

### 测试稳定性（附带修复）

`step14` E8 曾是 CI 上的 flaky：乐观移除→DELETE 500→回滚整个闭环只持续几十毫秒，
用 `waitForFunction` 轮询等于在采样瞬时状态，轮询一漂移就整段错过。
改为**点击前挂 MutationObserver，把"曾经消失过"记成粘性标志**后再断言，根治。

## 四、优化后复测

| 页面 | LCP（优化前） | LCP（优化后，多轮） | 静态边缘命中 |
|---|---|---|---|
| 首页 | 1532ms | 2092ms | **7/12** |
| 文章列表 | 1464ms | 1504ms | **7/11** |
| 文章详情 | 3784ms | 1740ms / 2976ms | **7/11** |
| 相册 | 4256ms | 3116ms / 4556ms | **7/12** |
| 网盘 | 1352ms | 1720ms / 2228ms | **7/9** |
| 小游戏 | 1112ms | 2104ms / 4368ms | **8/12** |

### 稳定改善（可确证）

- **静态资源边缘命中：0/12 → 7~8/12**（三轮均稳定）—— 11~12 个资源不再每次回源。
- **API 边缘缓存从"零命中"到普遍 HIT**：`/api/site`、`/api/music`、`/api/posts`、
  `/api/album/photos` 均出现 `cache=HIT`，`age` 持续增长；耗时从 250~650ms 降到 163~191ms。
- **最坏等待从 8s 降到 3s**：单源熔断，配合换源与重试。

### 波动项（需如实说明）

LCP 单次采样波动达 1~4s（小游戏第 3 轮 4368ms、相册 3116~4556ms），
**波动源不在本站，而在第三方与大图**：

| 干扰项 | 实测耗时 | 说明 |
|---|---|---|
| `static.cloudflareinsights.com/beacon.min.js` | 600~1928ms | 同步脚本，阻塞渲染 |
| `cloudflareinsights.com/cdn-cgi/rum`（POST） | 700~3321ms | 页面最慢请求之一 |
| `https://example.com/cover.jpg` | 700~1900ms，**每页 FAILED** | 内容仓库里的示例封面，域名不可达，白白失败 |
| 相册 raw 原图 | 1198~1811ms（已 `cache=HIT` 仍慢） | 手机截图原图，体积过大 |

即：**缓存层已优化到位，LCP 现在由第三方脚本和大图主导**，继续优化须处理这四项。

---

## 五、下一步建议（按性价比排序）

1. **移除失效占位图 `example.com/cover.jpg`**（每页一个失败请求，700~1900ms）
   —— 属内容仓库 `Blog` 的示例数据，建议换成真实封面或本地占位图。
2. **CF Insights 的 beacon/RUM 改为异步加载**（或直接关闭 Web Analytics）
   —— 同步 `beacon.min.js` 直接卡在关键路径上。
3. **相册生成缩略图**：原图直传导致 `cache=HIT` 仍要 1.6s，缩略图可降一个数量级。
4. **消除剩余重复请求**：相册 `<img>` 与懒加载各触发一次、网盘初始化与解锁各调一次。
5. **其余页面接入 BlogApi**（blog / post / links / timeline / games 仍在用裸 fetch），
   统一获得 3s 熔断 + 去重 + 缓存降级。
